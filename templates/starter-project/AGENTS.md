## 项目结构

- 用真实项目的顶层目录替换这里。
- 常见示例：
  - `src/` 或 `app/`：主应用代码
  - `packages/`：monorepo 中的共享库
  - `scripts/`：工具脚本或维护脚本
  - `docs/`：roadmap、spec、架构说明
  - `tests/`：自动化测试

## 开发规则

- 修改前先探索相关文件。
- 始终按小而可验证的切片推进。
- 汇报完成前，先运行与项目相关的真实验证命令。
- 如果项目有 lint 或类型检查，也要跑。
- `git add` 只允许显式文件路径，不用 `git add .`。
- 不要硬编码密钥、密码或私有令牌。
- 不要通过削弱测试来掩盖实现错误，除非测试本身就是错的。
- 优先扩展现有模块，不要平行再造一套实现。

## 完成标准

在汇报任务完成前：

1. 跑项目真实相关的验证命令。
2. 如适用，跑 lint 或类型检查。
3. 检查边界情况与回归风险。
4. 运行 `/review`，或给出等价的审查总结。
5. 如果这次改动改变了项目状态，同步 roadmap、spec 或 session-notes。

## 路线图与规格

- 如果任务属于计划内功能，先读 `docs/roadmap/README.md`。
- 如果 `docs/specs/` 里已有相关 spec，实施前先读。
- 功能切片完成后，在 commit 前先同步 roadmap 或 spec 状态。

## Git 规则

- 使用 Conventional Commits。
- 一个 commit 只对应一个可验证切片。
- 验证和审查没完成前，不进入 push。
